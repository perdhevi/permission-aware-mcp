# Security boundaries

1. MCP arguments and request metadata are untrusted. `whoami` accepts only an
   empty object, with `additionalProperties: false`. Identity fields are absent
   from its input schema. Client metadata cannot populate SDK token information.
2. Caller identity comes exclusively from bearer-token authentication. The verifier
   pins RS256 and either a configured development RSA public key (at least 2048 bits)
   or OIDC-discovered JWKS, and requires a
   valid signature, issuer, audience, expiration, nonblank subject and exact scope.
   Present `nbf` claims are also validated. Unknown signing algorithms are rejected.
3. Tenant membership is derived from the database lookup by `(issuer, subject)`.
   JWT tenant claims, client arguments and headers cannot select the tenant.
   Unknown or inactive local users are rejected, even with a cryptographically valid token.
4. Roles come from the database. Tokens supply no authoritative application roles
   or tenant selection. Explicit user or role read ACLs are required, even for
   `executive`; there is no implicit hierarchy or administrator bypass.
5. Retrieval constrains candidates by tenant, active user and current document ACL
   in a materialized CTE **before** similarity ranking and limiting. Post-filtering
   top-K results is insufficient. Role names supplied in principals grant no access.
6. Retrieved document content is data, never authorization instructions. Hostile
   text cannot change a principal or grant access to additional resources.
7. Direct reads independently recheck current active tenant membership and ACLs
   every time, including after listing or search. Missing, malformed UUIDs and inaccessible
   documents return the same generic tool error. Lists expose only authorized
   UUIDs and titles, with no total count or ACL details. Composite database foreign
   keys reject cross-tenant user roles and ACL grants. Resource query failures
   return a generic unavailable error without database diagnostics or partial results.

Every MCP request passes through the official SDK bearer middleware. Stateless
HTTP avoids persistent session identity; no principal is captured in a server
closure or accepted from request parameters. The SDK sees the local user UUID in
`TokenInfo.UserID`. Verification failures use a generic error, not raw JWT parser
messages or database errors. Database unavailability fails closed.

The development token CLI signs only issuer, subject, audience, scope, issued-at
and expiration. It does not select tenant or roles. Minting a valid token for an
unregistered subject does not create a user. Tokens, Authorization headers, private
keys and raw claims are never logged. `whoami` returns only local UUID, subject,
tenant slug, database roles and scopes. Request IDs are generated by the server,
replacing client values. Resource calls log ALLOW/DENY/ERROR decisions with caller
and request correlation, without document contents or raw database diagnostics.
Every authenticated `tools/call` is persistently audited, including SDK schema
rejections, unknown tool names and denied direct reads. Fixed reason categories
avoid storing raw error text. Unknown names are recorded as `unknown`. Query text
is stored only as an unsalted SHA-256 hash; common queries remain guessable, so
audit records are sensitive operator data. No token, arguments, content, title,
embedding or ACL metadata is stored. Denied and missing resources share the reason
`not_found_or_forbidden`; no unrestricted existence probe is made.

Audit writes have a separate two-second timeout and survive request cancellation.
Results are withheld if writing fails, with a sanitized operational error log.
The database decision and audit insert are separate operations: an ALLOW records
the read decision, not proof of delivery. Process crashes and storage outages can
leave gaps; storage failures cannot themselves be persisted to unavailable storage.
No tamper resistance, retention job, separate audit DB role or administrative MCP
reader is implemented. The development database owner remains trusted.
HTTP authentication failures and messages rejected before SDK tool dispatch have
no authenticated tool event; only normal HTTP operational logging applies.
The optional hostile-content demo and deterministic host-follow-up tests are in
[Phase 04](phase-04.md). No live language-model behavior is assumed or measured.

Search accepts only query and limit. It returns authorized chunk IDs, document IDs,
titles, bounded text and distances, with no candidate totals or ACL metadata.
Raw queries, embeddings and retrieved text are not logged. Search/embedding failures
produce a generic unavailable tool error. The local embedder makes no external calls.
Ingestion is a trusted database administration CLI and can read every document in
the selected tenant; do not expose its credentials as an end-user capability.
Chunk foreign keys bind tenant and document. Source-content hashes exclude stale
chunks until re-ingestion; MD5 is an operational change detector, not a security
signature against a malicious database administrator. Database administrators remain trusted.

This milestone supports local development deployments with either dev JWTs or
real Keycloak OIDC/OAuth. Keep the server and database on localhost. The local
Keycloak profile uses public fixture credentials and `start-dev`; it is not a
production identity service. OIDC uses configured issuer discovery, bounded HTTP,
no redirects, RS256 JWT signature/claim checks and payload `typ=Bearer` to reject
Keycloak ID tokens. Cleartext provider URLs are allowed only on literal loopback
hosts; HTTPS issuers cannot downgrade JWKS to HTTP. The library applies up to two
minutes of clock skew for `nbf`. Errors omit raw parser/network/claim diagnostics.

OAuth scope grants entry, never tenant or document privileges. The canonical
resource URL must match the token audience. Public protected-resource metadata
and bearer challenges use operator configuration, not forwarded/Host headers.
The PKCE CLI uses random state, S256 and an exact loopback redirect; direct password
grants are disabled. Other hosts need explicitly registered clients/callbacks.
No token introspection, refresh persistence or immediate logout/revocation exists.
Cached known keys can verify tokens during provider outages or after issuer key
removal until expiry; new keys need a successful refresh. Unknown-key traffic may
cause refresh load; rate limiting remains deferred. Local deactivation is immediate
on the next request. See [Phase 05](phase-05.md) for the supported provider profile.

In optional dev mode the issuer is only an identifier, not an OAuth server.
Deleting a private key does not revoke tokens already signed with it; changing the
configured verification key requires server restart. Keep local key files private;
Windows requires ACLs because Go's Unix file modes do not enforce Windows permissions.

The readiness endpoint checks database connectivity, not schema compatibility.
The migration must be applied before MCP calls can resolve users. Compose credentials
are public development defaults and must not be reused for production.
