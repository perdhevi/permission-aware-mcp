# Phase 00 — Project skeleton and database

## Scope and outcome

This phase establishes the Go module, package boundaries, environment configuration,
local PostgreSQL with pgvector, initial database schema, seed identities, and process
health endpoints. It provides the foundation for authenticated MCP access in
[Phase 01](phase-01.md).

Phase 00 and Phase 01 were implemented together in the initial pass. The files
described here are the foundation of the current combined implementation; this
document does not describe a separately runnable historical Phase 00 checkout.
In particular, starting the current server requires Phase 01's public key.

## Database design

`tenants` has a UUID primary key, unique slug, name, and creation timestamp.
`users` has a UUID primary key, tenant foreign key, issuer, subject, display name,
active flag, and creation timestamp. Required fields are nonnull and external
identities have the unique constraint `(issuer, subject)`.

The migration runs `CREATE EXTENSION IF NOT EXISTS vector`. Embedding columns and
document tables are intentionally deferred. pgvector is available but unused by
the authentication slice.

The seed creates tenant `acme` and active subjects `alice`, `bob`, `carol`, and
`dave`, all with issuer `http://dev.local`. UUIDs are generated by PostgreSQL and
will differ between fresh databases. No roles are assigned in this phase.

Compose mounts `migrations/` into `/docker-entrypoint-initdb.d` and stores database
data in a named volume. Initialization scripts run only on a fresh database volume.
Restarting the container preserves data and does not reapply migrations. The
initial migration is not an idempotent upgrade script; use the instructions in
[seed/README.md](../seed/README.md) only if applying it to an existing empty schema.

## Configuration and startup behavior

| Variable | Development default | Purpose |
| --- | --- | --- |
| `APP_ENV` | `development` | Only supported application environment in this pass. |
| `HTTP_ADDR` | `127.0.0.1:8080` | Local HTTP listener. |
| `DATABASE_URL` | `postgres://permission_mcp:permission_mcp@localhost:5432/permission_mcp?sslmode=disable` | Local development database connection. |
| `AUTH_MODE` | `dev` | Only supported authentication mode. |
| `AUTH_ISSUER` | `http://dev.local` | Required JWT issuer and database external identity issuer. |
| `AUTH_AUDIENCE` | `permission-aware-mcp` | Required token audience. |
| `DEV_JWT_PUBLIC_KEY_FILE` | `.local/keys/public.pem` | Public key loaded at startup. |
| `REQUIRED_SCOPE` | `knowledge:read` | One required scope; empty or multiple configured scopes are rejected. |

The Go programs read the process environment. Copying `.env.example` to `.env`
does not load it into Go automatically. Export overrides in the terminal before
running commands. Defaults are restricted to development; setting `APP_ENV` to
`production` intentionally fails rather than using development authentication there.

Startup checks database connectivity with a five-second timeout. `/healthz`
returns 200 when the process is serving; `/readyz` checks PostgreSQL connectivity
with a two-second timeout and returns 503 if it fails. Readiness does not verify
schema compatibility. A database with missing tables can pass readiness and still
fail identity lookup.

## Validation steps

Run commands from the repository root. Examples use PowerShell 7. Prerequisites
are Go 1.27.1 or later, Docker Desktop or another running Docker engine, Compose
v2, and available local ports 5432 and 8080. Initial dependency/image downloads
require network access.

### 1. Confirm prerequisites and Compose configuration

```powershell
go version
docker version
docker compose config --quiet
```

Expect Go to report a compatible version, Docker to report both client and server,
and Compose configuration validation to exit successfully without output.

### 2. Start PostgreSQL

```powershell
docker compose up -d --wait
docker compose ps
```

Expect the `postgres` service to become healthy and port 5432 to bind to localhost.
If initialization fails, inspect `docker compose logs postgres` before proceeding.

### 3. Check the extension and seeded identities

```powershell
docker compose exec -T postgres psql -v ON_ERROR_STOP=1 -U permission_mcp -d permission_mcp -c "SELECT extname FROM pg_extension WHERE extname = 'vector';"
docker compose exec -T postgres psql -v ON_ERROR_STOP=1 -U permission_mcp -d permission_mcp -c "SELECT t.slug, u.issuer, u.subject, u.active FROM users u JOIN tenants t ON t.id = u.tenant_id ORDER BY u.subject;"
```

Expect one extension row named `vector`, then four user rows. Every user should
belong to `acme`, use issuer `http://dev.local`, and have active flag `t`.

### 4. Start the current server

Generate the development key pair once if neither key exists:

```powershell
go run ./cmd/devtoken keygen
```

If the pair already exists from Phase 01, reuse it. Key generation deliberately
refuses to overwrite either existing key. Do not delete working keys just to repeat
this validation. Start the server in this terminal:

```powershell
go run ./cmd/server
```

Expect a structured `server listening` log for `127.0.0.1:8080`. Leave the process
running while checking endpoints from a second terminal.

### 5. Check health and readiness

```powershell
(Invoke-WebRequest http://127.0.0.1:8080/healthz).StatusCode
(Invoke-WebRequest http://127.0.0.1:8080/readyz).StatusCode
```

Both should return 200. Neither requires a bearer token. Process health and
dependency readiness are tested separately by `TestReadinessFailure` using a fake
unavailable database, without stopping the shared development container.

### 6. Run static checks and database integration tests

```powershell
gofmt -l cmd internal
go vet ./...
$env:TEST_DATABASE_URL = 'postgres://permission_mcp:permission_mcp@localhost:5432/permission_mcp?sslmode=disable'
go test -count=1 -v ./internal/config ./internal/repository/postgres
```

Expect no filenames from `gofmt`, no diagnostics from `go vet`, and passing tests.
Use `-v` to confirm `TestUsersIntegration` actually ran. Without `TEST_DATABASE_URL`
that test is skipped, so an otherwise green suite does not prove database integration.

## Automated test coverage

| Test | What it validates |
| --- | --- |
| `TestFailClosedConfiguration` | Rejects unsupported environment/authentication modes, missing issuer/audience/database URL/scope, and multiple configured scopes. |
| `TestUsersIntegration` | Resolves all four real seeded users, checks tenant and active status, rejects unknown subjects and incorrect issuers, rejects a dedicated inactive test user through the resolver, and confirms the vector extension. |
| `TestReadinessFailure` | Returns 200 for process health and 503 for database readiness when the database pinger fails. Located in the MCP server tests. |

The integration test removes its dedicated inactive user after execution and does
not modify the seeded users. Authentication-specific tests are listed in Phase 01.

## Validation record and troubleshooting

During the initial implementation on 2026-10-19, Compose started PostgreSQL
successfully; real database integration tests confirmed seed identities and
pgvector; both HTTP health endpoints returned 200; formatting and `go vet ./...`
passed. The uncached full test suite passed with `TEST_DATABASE_URL` configured.
These are recorded implementation results, not a claim that services are currently running.

- Docker pipe/socket errors usually mean the engine is stopped or inaccessible.
  Start Docker Desktop and retry `docker version`.
- A port conflict on 5432 or 8080 requires freeing that port or adjusting both the
  listener/port mapping and the corresponding connection configuration.
- Missing seed tables on an old volume mean initialization did not run for that
  volume. Inspect its schema and the seed notes before applying any migration.
- A missing public key requires the one-time Phase 01 key generation step.
- `.env` overrides that appear ineffective must be exported into the Go process environment.

## Limits and next step

This phase has no migration version runner, production authentication, document
schema, RBAC, ACL enforcement, embeddings, or retrieval. Development database
credentials are public defaults. Continue with [Phase 01](phase-01.md) to validate
the authenticated MCP path; Phase 02 should implement database roles and document ACLs.
